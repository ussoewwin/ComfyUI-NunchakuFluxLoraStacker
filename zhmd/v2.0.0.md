# v2.0.0 — Model Patch Loader ConvRot INT8 支持

本发行说明说明 **Model Patch Loader**（`ModelPatchLoaderCustom`）如何原生加载 comfy 原生 **ConvRot INT8** 量化的 Z-Image ControlNet 检查点，以及为什么此前会崩溃。

**相关**

- 功能实现：`nodes/misc_v2.py`（提交 `ac4097f`）
- 技术说明：[CONVROT_INT8_MODEL_PATCH_LOADER_EXPLANATION.md](CONVROT_INT8_MODEL_PATCH_LOADER_EXPLANATION.md)（英文：[md 同名文件](../md/CONVROT_INT8_MODEL_PATCH_LOADER_EXPLANATION.md)）

---

## 1. 目的

**Model Patch Loader**（`ModelPatchLoaderCustom`）此前只能加载浮点精度的模型补丁（BF16/FP16/FP32）。当用户选择 ConvRot INT8 量化的 Z-Image ControlNet 检查点（`Z-Image-Turbo-Fun-Controlnet-Union-2.1-lite-2601-8steps_convrot_int8.safetensors`）时，节点会立即崩溃：

```
RuntimeError: Only Tensors of floating point and complex dtype can require gradients
```

本次更改的目标是让 Model Patch Loader **原生加载 ConvRot INT8 ControlNet 检查点**，从而：

- 权重在内存（VRAM 或系统内存）中以 **INT8 形式保存** — 大致是 BF16 原始文件的一半（本模型磁盘占用 963 MB vs 1923 MB）。
- 前向计算走 comfy-kitchen 的 `int8_linear` 内核，带 **在线 ConvRot（Hadamard）激活旋转**，与 ComfyUI 自身 INT8 UNet/CLIP 加载相同的优化路径。
- 加载器对既有的全部 BF16/FP8 补丁 **100% 向后兼容** — 无需修改工作流或用户操作。

## 2. 为此需要做什么

### 2.1 根因分析

旧代码是这样做的：

```python
dtype = comfy.utils.weight_dtype(sd)   # 对 INT8 检查点会返回 torch.int8！
...
model = ZImage_Control(dtype=dtype, operations=comfy.ops.manual_cast, ...)
```

`weight_dtype()` 按张量元素数计算主导 dtype。在 INT8 检查点中 INT8 权重张量占多数，于是加载器拿到 `dtype=torch.int8` 并尝试用它构建模块图（RMSNorm 权重、Linear 偏置等）。随后 `torch.nn.RMSNorm` 调用 `torch.empty(..., dtype=torch.int8)` 并包装为 `Parameter(..., requires_grad=...)` — 整数 dtype 这样做是非法的。于是在触及任何 state dict 之前就崩溃了。

另一个更隐蔽的问题：旧代码无条件执行 `z_image_convert(sd)`，这是面向 **diffusers 风格** Z-Image 布局的键重命名工具（`to_q`/`to_k`/`to_v` → 融合 `qkv`，`norm_q` → `q_norm` 等）。而 INT8 检查点分发时已是 **comfy 原生布局**（`attention.qkv.*`、`attention.out.*`），对它来说转换是空操作 — 但仍要跳过，否则有破坏量化键分组的风险。

### 2.2 参考实现

姊妹仓库 `ComfyUI-HSWQ-Loader-and-Tools` 已在其独立 ControlNet 加载器（`nodes/hswq_load_convrot_int8_controlnet.py`）中解决了这两个问题。其手法：

1. **检测** — 扫描 state dict 中字节编码 JSON 的 `<layer>.comfy_quant` 条目，命中 `"format": "int8_tensorwise"` 即为 INT8。
2. **强制图 dtype 为 BF16** — 使模块图可以构建。
3. **换用感知量化的 ops 类** — `comfy.ops.mixed_precision_ops({"int8_tensorwise": QUANT_ALGOS["int8_tensorwise"]}, torch.bfloat16)`。其 `Linear._load_from_state_dict` 会消耗 `<layer>.comfy_quant` + `<layer>.weight_scale`，并给每个 Linear 接入 INT8 `QuantizedTensor`（`TensorWiseINT8Layout`，含 `convrot=True` 与 `convrot_groupsize`），而非普通权重。

### 2.3 实现前的可行性验证

- **检查点分析**（自写 safetensors 头解析器）：157 个键，38 个量化层，每个 `comfy_quant` 均为 `int8_tensorwise` + `convrot: true`；groupsize 直方图 `{256: 37, 4: 1}`（`4` 是 `control_all_x_embedder.2-1`）。
- **内核可用性**：确认 comfy-kitchen 的 `eager` 后端在 CPU 张量上实现了 `int8_linear`（所以 `cpu_offload=True` 可用），CUDA 后端覆盖 GPU 执行（RTX 5060 Ti，INT8 张量核需 SM ≥ 7.5）。
- **量化路径机制**：阅读 ComfyUI 的 `comfy/ops.py`（`_load_quantized_module`、`mixed_precision_ops`）确认 `comfy_quant`/`weight_scale` 的消耗契约，以及 `cast_bias_weight` 在层被移到 CPU 或动态挂 LoRA 时会优雅反量化（失效安全，不会硬崩溃）。

#### (b) 新增辅助函数（插入到 `z_image_convert` 之前）

```python
def _decode_comfy_quant(raw) -> dict:
    try:
        return json.loads(raw.numpy().tobytes())
    except Exception:  # noqa: BLE001
        return {}


def _has_int8_comfy_quant(sd) -> bool:
    """True if the checkpoint carries >=1 int8_tensorwise comfy_quant layer (ConvRot INT8)."""
    for key in sd.keys():
        if not key.endswith(".comfy_quant"):
            continue
        conf = _decode_comfy_quant(sd[key])
        if conf.get("format") == "int8_tensorwise":
            return True
    return False


def _int8_mixed_precision_ops():
    """MixedPrecisionOps supporting int8_tensorwise (ConvRot included).

    Same approach as the HSWQ ControlNet loader: build the module graph in a
    float dtype (BF16) and let MixedPrecisionOps.Linear._load_from_state_dict
    consume "<layer>.comfy_quant" / "<layer>.weight_scale", attaching an INT8
    QuantizedTensor (TensorWiseINT8Layout) to every quantized Linear.
    """
    quant_config = {
        "int8_tensorwise": QUANT_ALGOS["int8_tensorwise"],
    }
    return comfy.ops.mixed_precision_ops(
        quant_config,
        torch.bfloat16,
        full_precision_mm=False,
        disabled=[],
    )
```

## 5. 意义与影响

### 5.1 加载流程对比

| 阶段 | BF16 检查点（不变） | ConvRot INT8 检查点（新） |
|---|---|---|
| dtype 检测 | `weight_dtype(sd)` → BF16 | **强制 `torch.bfloat16`**（仅用于图构建） |
| ops 类 | `comfy.ops.manual_cast` | `mixed_precision_ops({int8_tensorwise}, bf16)` |
| 键转换 | `z_image_convert(sd)`（diffusers → comfy 布局） | **跳过** — 键已是 comfy 原生布局 |
| state dict 加载 | `load_state_dict` 直接赋值普通权重 | `_load_quantized_module` 弹出 `comfy_quant` + `weight_scale`，为每个 Linear 构建 `QuantizedTensor`（`TensorWiseINT8Layout`，`convrot=True`，groupsize 4/256） |
| 内存 | BF16 权重 | **INT8 权重**（约小 50%）；scale 是很小的 FP32 张量 |
| 前向 | 手动转换的 `F.linear` | comfy-kitchen `int8_linear` 内核；激活的在线 Hadamard 旋转与旋转后的权重匹配（`convrot_groupsize`） |
| CPU 卸载 | 原生支持 | 可用 — `eager` 后端在 CPU 上实现 `int8_linear`；若层必须在 CPU 上计算，`cast_bias_weight` 会安全反量化 |

### 5.2 为什么这个设计是安全的

- **检测基于元数据而非文件名。** 只有字面上含有 `format` 为 `int8_tensorwise` 的 `comfy_quant` 条目的文件才会走 INT8 路径，命名错误或部分量化的文件不会误触发。
- **BF16 路径逐字节等于旧路径。** 对非 INT8 文件唯一的行为变化是 `operations` 改走一个变量，其值仍是原来的 `comfy.ops.manual_cast`。已通过回归测试验证。
- **不改核心。** 一切都在自定义节点内；只使用 ComfyUI 公开 API（`mixed_precision_ops`、`QUANT_ALGOS`、`weight_dtype`、`ZImage_Control`）。
- **优雅降级。** 若量化层被 LoRA 打补丁或被移到 INT8 内核无法运行的设备，ComfyUI 自身的转换逻辑会将该层反量化为 BF16 参与计算，而不是直接失败。

### 5.3 验证结果（RTX 5060 Ti，16 GB，ComfyUI portable）

1. **INT8 加载测试** — 目标检查点加载后 38/38 个 Linear 均接入 `QuantizedTensor` 权重（`torch.int8` 存储，`convrot=True`，groupsize 4/256）；日志 `[ModelPatchLoaderCustom] INT8 ComfyQuant detected ...` 确认新分支生效。
2. **前向计算（CPU 放置，即 `cpu_offload=True`）** — `forward`、`forward_control_block(0)`、`forward_noise_refiner_block(0)` 均返回形状正确（`[1, 64, 3840]`）且数值有限的输出。
3. **BF16 回归测试** — 未量化的 Union 检查点仍走 `manual_cast` + `z_image_convert`，量化权重为 **0**，同样通过前向检查。
4. **语法检查** — `py_compile` 无警告；`ComfyUI/custom_nodes` 中的部署副本与仓库副本哈希一致。

### 5.4 对用户的实际影响

- **963 MB** 的 ConvRot INT8 ControlNet 现在可通过 Model Patch Loader 加载运行，内存占用约为 BF16 版本（1923 MB）的一半，工作流不变（加载补丁 → 连接到 `ZImageFunControlnet` 应用节点）。
- `cpu_offload=True` 时系统内存占用同样减半；只要层在 GPU 上，计算始终走优化的 INT8 路径。
- `HSWQ ControlNet Loader` 的用户获得完全相同的 INT8 语义，但这里是补丁式工作流（VAE 编码控制图、强度、掩码、局部重绘支持），而非 `CONTROL_NET` 对象工作流。
